Branch `work-mobile`, from master `7b6877d` (server 1.6.85). Harness and how to re-run everything: `tools/mobile-perf/README.md`. Every table in full: [`TABLES.md`](TABLES.md) (generated by `tools/mobile-perf/summary.js`).

Repeat visits were 96–100 before and are 96–100 after. Accessibility 100, SEO 100, Best Practices 96–100 on every route, before and after.

**The three biggest bottlenecks found**

1. **Work for later was done first.** While boot waited for its own answers the app fetched ten more screens' code (160 KB, the player included) and installed the offline worker, which downloaded the whole app a second time (74 requests, 760 KB) — all at the priority of what the first screen was waiting for. On Slow 3G that was 310 KB ahead of Home's own data.
2. **Boot was a queue of round trips.** Code in three waves (the preload list had fallen four modules behind), then *who is signed in* → *profiles* → *watch state* → *Home*, one after the other: seven round trips before the first row could be drawn, on a line where one is half a second.
3. **The code itself was heavy and never cached.** 313 KB of JavaScript on the wire, half of it comments; every visit re-asked the server about each of 48 modules.

On a slow *processor* the picture is different and less was won: see "What a slow phone spends its time on" and "What is left".

**What was changed** — eight changes, each its own commit, each measured alone, none of which moves a pixel (see "Pixels"):

| | Change | Measured gain |
|---|---|---|
| 1 | Shelf arrows are not measured where CSS hides them (phones, touch) | Home on a slow phone: blocking time 1396 → 1240 ms, forced layouts 57 → 36 |
| 2 | The nav's tone reads each element once per measure | scrolling Home: blocked time 372 → 162 ms, slowest input→paint 168 → 96 ms |
| 3 | Other screens' code and the offline worker wait for the first screen | Slow 3G first visit: 11 s → 7.2 s |
| 4 | Modules served without comments, pre-compressed, content-addressed + import map; preload list generated | Slow 3G first visit 7.1 → 5.7 s, repeat 3.6 → 2.8 s; JS 313 → 155 KB |
| 5 | The worker's copy of the app reuses what the page downloaded | first visit −250 KB (1516 → 1264 KB) |
| 6 | Boot's four questions are asked in parallel with the code | Slow 3G first visit 6.0 → 3.7 s, repeat 3.0 → 1.7 s |
| 7 | Episode stills through the server's picture cache | third-party requests on a series page: one per still → 0 |
| 8 | A page opened on another screen preloads that screen's code | 1.5 Mbit/s first visit: film page 3.6 → 2.6 s, Movies 4.0 → 3.2 s, Search 1.8 → 1.2 s |

Tried and dropped: remembering the window's width instead of re-reading it while Home builds (it removed 9 forced layouts and no time: the layout it skipped is one the page needs anyway).

**Proposed, not done, because a person could see it** (numbers under "For the owner to decide"): episode stills at the size they are drawn; the billboard's landscape picture is downloaded on portrait phones only to tint the nav; Continue Watching stills at drawn size; placeholders only for the first shelves; the connection meter; a time limit on requests; fewer pictures at once; tap targets; and five more.

**What remains:** the processor side. Home still costs ~5 s of main-thread time in its first six seconds on a phone at a quarter speed (layout 1.0 s, script 1.4 s, the sky and the nav-tone measurer ~0.4 s each); title pages, the player and Search stay in memory after they are left; the connection meter misreads lines. All in "What is left".

**Tests:** `npm test` 853 tests, 845 pass, 8 skipped, 0 fail (master: 843 — the 10 new ones are `test/jsassets.test.js`), `npm run test:ui` 130 tests, 129 pass, 1 skipped, 0 fail — as on master. (Run four times: two of the runs made while this machine was also taking screenshots each lost one test to the load — a 15 s timeout once, the OS out of socket buffers once — a different test each time, each passing on its own.).

## How it was measured

Everything ran against a private instance (the UI tests' own), never the live server. Three additions make it representative:

- **A catalogue.** The instance's lookups to the catalogue service are answered from 400 made-up titles, so Home has a billboard and 17 shelves / 294 cards (the live Home: 10–14 shelves, ~240 cards, ~90 KB of JSON — shapes and sizes read from the live server, no data copied).
- **Pictures that weigh what real ones weigh.** Generated posters and backdrops tuned so the server's own resizer produces what it produces in the house: a phone poster 9–25 KB, a 780 px backdrop ~75 KB (live: 5–35 KB and 26–69 KB — the fixture leans heavy).
- **HTTP/2 in front**, as on the public site (`Via: Caddy`, h2): one multiplexed connection. (Bare HTTP/1.1, as on the home network's own address, was checked too: 1.5 Mbit/s first visit 5.2 → 3.3 s, repeat 4.6 → 1.6 s.)

**Lines** are the repo's `tools/throttle-proxy.js` — real bandwidth and latency on every byte, the service worker's and the TLS handshake's included: Slow 3G 400 kbit/s · 400 ms; "regular 3G" 1.5 Mbit/s · 300 ms; 3 Mbit/s · 150 ms. **The phone** is Chrome's CPU throttle, ÷4 and ÷6. **Viewports:** 360×740 @3, 390×844 @3, 412×915 @2.6, 820×1180 @2, 1440×900 @1.

**Cold** = no HTTP cache, no service worker, the profile remembered (a phone after a deploy, or after the browser dropped its cache). **Warm** = the visit right after.

Two things to hold against every number:

- **The machine was busy.** It ran at 100% CPU throughout (other work, not this). So nothing here was measured alone: "before" (a snapshot of the baseline commit) and "after" ran *at the same moment*, side by side, and what is reported is the pair. Absolute times are pessimistic and vary from table to table; the differences within a pair are what to trust. ÷4 on this desktop under that load is roughly a mid-range Android phone of a few years ago.
- **Lighthouse's `mobile` numbers are simulated** (that is what the Lighthouse panel and PageSpeed do), and its simulation does not see a service worker's own traffic — its repeat-visit numbers flatter both versions. The slow-line tables are measured for real.

Third parties: Chrome was run with every host name but this machine unresolvable, so any call out fails and is listed. **The site calls nobody at runtime — with one exception that was found and removed** (episode stills, change 7). YouTube (billboard trailers) is the deliberate other one and is not requested on a slow line, with data saver, or on a touch phone by default.

## The bottlenecks, ranked

1. **Not-yet-needed downloads at the front of the queue** (line). Evidence: the Slow 3G waterfall — at 1.5 s, ten `import()`s at *High* priority (player.js 72 KB, discover-detail.js 36 KB…), fired from a `requestIdleCallback` that runs the first time boot waits on the network; at 2.2 s the service worker's install starts 74 fetches with `cache: "reload"`, also *High*, 760 KB in all; `/api/home` goes out at 2.4 s behind all of it. → changes 3 and 5: 11 s → 7.2 s.
2. **Seven round trips in a row before the first shelf** (line). The page → the stylesheet and 24 preloaded modules → four more modules the preload list did not know (`net`, `blur`, `artUpgrade`, `glassTone`: two more levels) → `/api/me` → `/api/profiles` → the watch state → `/api/home`. → changes 4 (list generated) and 6 (questions asked from the page): 6.0 s → 3.7 s on Slow 3G, and the same seconds on a *repeat* visit, where nothing else was left to save.
3. **313 KB of JavaScript, re-validated on every visit** (line, and parse time). Half of every module is comments. `Cache-Control: no-cache` on all of it: 48 conditional requests per visit, each through the service worker. → change 4: 155 KB, immutable.
4. **Layout** (processor): ~1 s of Home's first six at ÷4, and two tasks of 400+ ms each. Largely the browser's first text shaping, not the page's size; partly forced from script while Home is still being built (45 of 59 layouts). → change 1 removes the rowArrows share; the rest is in "What is left".
5. **Standing work that never stops** (processor): the nav-tone measurer (every 1.2 s, after every scroll event and every picture: 65–97 ms a time at ÷4) and the sky. → change 2 trims the first; proposals 10 and 11.
6. **Pictures the phone does not show** (line, data): a 26–69 KB landscape backdrop per billboard slide on portrait phones, fetched only to compute the nav's tint; episode stills at 780 px from a third party; 44–50 posters at once on Home. → change 7, proposals 1–3 and 7.
7. **Screens that are never freed** (memory): title pages, the player, Search. → "Bugs found on the way".

## What was changed

Each was measured alone: its commit against the commit before it, both running at the same moment. All are behaviour-preserving; "Pixels" below is the proof for the whole set.

### 1. Shelf arrows are not measured where nobody can see them — `public/js/rowArrows.js`

The left/right arrows on a shelf exist only under `(hover: hover) and (pointer: fine) and (min-width: 861px)`; `components.css` hides them otherwise, and nothing else reads `can-prev` / `can-next` or the `--row-nav-*` variables. Yet every shelf was measured for them on every device: `scrollWidth`, two `getBoundingClientRect`s and a `getComputedStyle` per shelf, interleaved with style writes — a forced layout per shelf while Home builds, and again on every scroll event of a sideways swipe. Where the query does not hold, the measuring is skipped. The query is live (a mouse plugged into a tablet, a window widened): on a change every row measures itself.

- **Home, ÷4, 5 runs:** blocking time 1396 → 1240 ms; main thread 5383 → 4909 ms (style 667 → 446, layout 1035 → 921); long tasks 20 → 15; forced layouts 57 → 36.
- **Risk:** a device where the arrows are visible but the query says otherwise — there is none: it is the same query, in CSS and in script. Desktop is untouched (the query holds; the same code path as before).

### 2. The nav's tone reads each element once per measure — `public/js/navTone.js`

A measure asks what is behind ~20 points under the nav. The same elements sit under most of them, and each one's box, computed style and two pseudo-elements were read again per point. Now read once per measure; only the lookup at the point repeats. The arithmetic is the same, in the same order.

- **Scrolling Home, ÷4, 3 runs:** time blocked by long tasks 372 → 162 ms; slowest input → paint 168 → 96 ms. While Home loads, navTone's own time 295 → 245 ms.
- **Risk:** none found — nothing on the page can change inside one synchronous measure.

### 3. Other screens' code and the offline worker wait for the first screen — `public/js/main.js`

Both hung off "the browser is idle" at boot, and a phone is idle every time boot waits for the network. Both now wait for *the first screen has painted and the pictures in view have arrived* (or 6 s; 12 s on a line the app has classed slow; 4 s if only the profile door is up). The screens are then warmed one at a time, each in an idle slice. The New tab's dot keeps its old moment — it is the one part a person can see arrive.

- **Slow 3G, first visit, 5 runs:** usable 11 s → 7.2 s; first screen complete 13 s → 9.0 s; on the wire before usable 67 requests / 430 KB → 44 / 215 KB. At 3 Mbit/s: 3.6 s → 3.7 s — no change; there the line was never what Home waited for.
- **Risk — the one trade in this report:** a tap on another tab *before* the first screen has settled now fetches that screen's code on demand (5–18 KB), where before it was usually already there. It is the code path a fast tapper already took, it shows the same skeleton, and on Slow 3G the old warm-up was itself not finished until ~8 s in. Change 8 covers the case where the page is *opened* on another screen.

### 4. Modules without comments, pre-compressed, cached for good — `src/lib/jsassets.js`, `src/lib/assetver.js`, `server.js`

- **Re-printed.** esbuild prints each module without comments and layout whitespace (`minifyWhitespace` only — no renaming, so a stack trace still names real functions). 971 KB of source → 498 KB to parse. esbuild is an *optional* dependency: where it is not installed every file is served as written and everything else still works.
- **Content-addressed.** Every module has a URL with its hash (`/js/ui.js?v=…`), answered `immutable`. An **import map** written into the page maps each module to it — so `import "./ui.js"` inside any module lands on the cacheable address without a hash being written into any file, one changed module changes one URL, and a repeat visit asks the server about no JavaScript at all. A browser without import maps (iOS before 16.4, Chrome before 89) ignores the map and gets exactly the old behaviour: `no-cache`, an ETag, 304s. A request under an *old* hash is answered with the current code but not as immutable.
- **Pre-compressed.** Brotli 11, once, in the background, sent from memory; until it is ready the existing on-the-fly brotli 6 answers. The stylesheet bundle too: 36.2 → 31.5 KB on the one request that blocks first paint.
- **The preload list is generated** from `main.js`'s imports when the page is served. Kept by hand, it was four modules behind.

On the wire: boot's modules 126 → 62 KB, all modules 313 → 155 KB; the page itself grows 3.7 → 5.4 KB (the map). **5 runs:** Slow 3G first visit 7.1 → 5.7 s, repeat 3.6 → 2.8 s; 3 Mbit/s first 2.8 → 2.6 s, repeat 3.5 → 3.2 s; bytes before usable 215 → 147 KB.

- **Risk:** a re-printer that changed meaning — it is esbuild's printer with every transform off, the browser suite (130 tests) runs on the re-printed code, and `test/jsassets.test.js` checks every module of the site parses and resolves. A deploy landing mid-load — unchanged from today (the page's existing one-reload guard). The editing loop — unchanged (a file's mtime or size changing rebuilds it on the next request). **To deploy:** `npm install` (for esbuild); without it the site runs as before, minus the smaller files.

### 5. The worker's copy of the app is no longer a second download — `public/sw.js`, `src/routes/api.js`

The worker fetched every file of the shell with `cache: "reload"`. It now asks with `no-cache` (the server is still consulted, so the copy is current) at the content-addressed URLs the page loaded, so the browser's own cache answers; four at a time, low priority. The six source stylesheets are no longer listed (the page loads the bundle; nothing ever asked the worker for them: 76 KB). A versioned file is kept under one cache entry instead of one per version, and a copy with holes is retried on the next load instead of being stamped complete.

- **First visit, 5 runs:** downloaded in all 1945 → 1693 KB (3 Mbit/s), 1516 → 1264 KB (Slow 3G). Time to usable: unchanged (after change 3 the worker was already out of the way).
- **Risk:** the update flow — the version stamp now also covers *what is served* (the re-printed bytes), so adding or removing esbuild refreshes the copy. Offline behaviour: every case of `resilience.js` is the same before and after.

### 6. Boot's questions are asked while the code is on its way — `public/index.html`, `public/js/api.js`, `state.js`, `main.js`

A small script at the top of the page sends `/api/me`, `/api/server-info`, `/api/profiles`, the remembered profile's watch state and (when Home is the page being opened) `/api/home` — with the headers the app would send. `api.js` hands each waiting answer to the call that would have made the request: once, only a 200, only while fresh (15 s); anything else is asked again the ordinary way, with the usual retries.

**Nothing is asked that boot would not ask.** What the device learned on its last visit decides: the sign-in mode (the profile list is asked for only where the last visit could read it — so the public sign-in page logs no new refusals), and how the remembered profile is entered — no password, this tab's unlock token, or (a kids profile, a locked one, nobody yet) only through its door, in which case nothing is asked early.

- **5 runs:** Slow 3G first visit 6.0 → 3.7 s, repeat 3.0 → 1.7 s; 3 Mbit/s first 3.1 → 2.3 s, repeat 2.3 → 1.6 s.
- **Risk:** a stale or wrong answer standing in for a real one — the guards above, plus: a first-ever visit asks only the two questions that need no sign-in. An answer to a question boot ends up not asking (the profile was deleted meanwhile) is simply dropped.

### 7. Episode stills through the server's picture cache — `public/js/ui.js`, `src/routes/stream.js`

A series page's stills were fetched by the browser straight from `episodes.metahub.space` — the one host missing from the picture proxy's two allow-lists: a second connection on a thin line, nothing kept by the server, and a third party told which series this household looks at (62 stills listed on the series checked on the live server, 95 KB each). Same bytes now, through `/img/ext`.

- Third-party requests on a series page: one per still → 0. Not resized (that changes the picture: proposal 1).

### 8. A page opened on another screen preloads that screen's code — `src/lib/assetver.js`

The page's preload script reads the address: on `#/movies`, `#/search`, a title, the player, Settings, Downloads it adds that screen's module and what it imports to the list. A reload on a title page, a restored tab, an installed app's "Search" shortcut no longer find out after boot that they need two more rounds of code.

- **1.5 Mbit/s, first visit, 5 runs:** a film's page 3.6 → 2.6 s; Movies 4.0 → 3.2 s; Search 1.8 → 1.2 s. Repeat visits: unchanged (the code is cached by then).
- **Risk:** the address → module table is kept by hand in `assetver.js`. A stale entry is a missing or wasted hint, never a failure.

## For the owner to decide — would help, but a person could see it

Ordered by what it buys.

1. **Episode stills at the size they are drawn.** One line (`artUrl(row.thumbnail, w)`). A still is 95 KB today (780 px JPEG; drawn 310 px wide on a glass phone, 88–176 px elsewhere). At the drawn size: ~40 KB on a 3× phone, ~18 KB on desktop — a season of ten saves 0.5–0.8 MB. Visible: the picture is then the server's WebP at quality 78 instead of the original JPEG scaled by the browser — the treatment every poster already gets.
2. **On a portrait phone, tint the nav from the picture that is on screen.** Home's billboard shows the *poster* in portrait, but `toneNavFromImage` is given the *landscape backdrop* — so each of the eight slides downloads a 26–69 KB picture nobody sees (0.2–0.5 MB per turn of the billboard, and on a first visit it competes with the first shelf). The title page already does it right (`details.js` uses the cover on a phone). Visible: the nav's tint on Home would follow the poster instead — arguably the fix of a small bug.
3. **Continue Watching stills at drawn size.** `/img/still/…` goes out as a 41 KB JPEG with no `?w=`; ~15 KB as a sized WebP. Same visibility as 1.
4. **Placeholders only where they will be seen.** The blur-up placeholders ride inside `/api/home`: 6 KB on the wire becomes 14–20 KB — for all 294 cards, on the one answer the first screen waits for. Sending them for the billboard and the first three shelves only would cut ~10 KB (0.2 s on Slow 3G). Visible: shelves further down would fade in from grey instead of from their colours, on the first visit.
5. **The connection meter misreads lines** (`js/net.js`). It times individual responses, and through HTTP/2 a response that waited in a queue and then arrived in one burst reads as tens of Mbit/s: the 400 kbit/s line was called **fast** on repeat visits (231 Mbit/s "measured"), the 1.5 Mbit/s line fast in 4 of 10 first visits, and the 3 Mbit/s line ended a five-minute session classed **slow**. So the light mode (1× pictures, no prefetch, no trailers) is neither reliably on where it should be nor off where it should not. A sturdier estimate — bytes over wall-clock time across all responses in a window, and the 48 KB probe run when the page is quiet rather than 1.2 s after load (where, now that boot is quick, it lands in the middle of the first screen's pictures) — is a behaviour change, hence here.
6. **A time limit on requests.** Nothing gives up: a server that accepts a request and says nothing leaves a skeleton (or, for the watch state, an empty page) for minutes. The TV app's rule would fit — give up after 45 s of silence and show the screen's existing "couldn't load" state with Try again.
7. **Fewer pictures at once on Home.** 44–50 posters are fetched on arrival (Chrome's lazy margin). An observer with a one-screen margin would fetch ~15. Visible: a fast flick could outrun the pictures by a moment (the placeholders would show).
8. **Split the stylesheet by screen.** 31 KB blocks the first paint and half of it is for screens not on show. Needs care to stay pixel-exact; worth ~0.3 s of first paint on Slow 3G.
9. **Tap targets:** the billboard's dots (21×33), ✕ on Continue Watching (24×24), "More" (35×29), tab bar items 40 px high. Larger hit areas need not change how they look (padding / `::after`), but they change what a near-miss does.
10. **The nav-tone measurer could skip pictures that are nowhere near the nav.** It re-reads the page 120 ms after *every* picture that arrives — ~400 ms of hit-testing in Home's first six seconds at ÷4. Skipping arrivals that do not overlap the nav would remove most of it; the tint could then change up to 1.2 s later in rare cases.
11. **The sky on weak phones.** ~0.4 s of main thread in Home's first six seconds at ÷4, and its first frame lands in the middle of boot. Starting it after the first screen (as change 3 does for code) or widening the "lite" tier (today: ≤2 cores or ≤2 GB) to 4 GB phones are both visible.
12. **`filter: blur(0px)` is left on every poster that sharpened in** (`.img-blurup.img-in`, `animation … both`). A no-op that still makes each such picture its own filter layer for as long as it lives, and it does not rasterise quite like no filter (this is what made the screenshots unrepeatable at first). Dropping the filter when the animation ends changes those pixels by a hair.
13. **Settings downloads the whole changelog** (43 KB compressed) on opening; Search's result posters are asked for without `?w=` (41 KB each instead of ~22). Both in files other branches are editing.

## Bugs found on the way (not fixed: other branches own the files)

- **Title pages, the player and Search are never freed.** Their screens stay in memory after they are left (+190 to +380 DOM nodes per title page visit). The likely pattern, in `screens/discover-detail.js` (lines ~1951, ~2592, ~2642, and `host._dlUnsub`), `screens/search.js` (~351) and `screens/details.js` (`coverDrift`): a listener on the live socket or on `window` that is removed *the next time its event arrives and finds the screen gone*. With no download running, `download_update` never arrives. Home does it right (it unsubscribes in the cleanup it returns to the router); these screens return no cleanup. The census (`leaks.js`, and detached `.screen` subtrees counted after a forced collection: 5 Search screens and 10 title pages alive after 5 visits each) is the evidence; the cause is read from the code, not proven with a heap snapshot — a `library_updated` message did not free the Search screens, so there is at least one more holder there.
- **After one online visit the app does not open offline** — see "When the line misbehaves". If that matters, the worker can fetch the four boot answers itself when it installs.
- **The nav's tint on portrait Home is computed from a picture that is not shown** — proposal 2.
- A series page asked a third party for every still — fixed (change 7).

## What is left

- **The processor side of Home.** ~5.0 s of main thread in the first six at ÷4 (was 5.2), blocking time ~1.2 s. In order: script (1.4 s: building 1150 elements, the nav-tone measurer, the sky), layout (1.0 s — see below), paint and compositing (0.8 s), style (0.5 s). The real lever is doing less: building only the shelves near the screen (the rest when scrolled to — it would have to be proven invisible, shelf by shelf, with scroll restoration), and not rebuilding Home from nothing on every Back.
- **The first layout.** 400+ ms at ÷4 for 38 objects, on this machine. If a phone shows the same (checklist below), the cure is in the font stack — fewer named fallbacks that do not exist on the device — and that is a visible change.
- **The leaks** above.
- **The connection meter** (proposal 5) — it decides how heavy every other page is.
- **Safari.** Nothing here was run on it.

## Not verifiable here — and a checklist for a real phone

Chromium on a desktop, with a throttle, is not a phone. Not covered: iPhone Safari at all; a real low-end Android (thermal throttling, slow storage, a small GPU, 2–3 GB of memory); a real radio (loss, jitter, a tower handover). Most likely to differ on Safari: the cost of `backdrop-filter` on the glass chrome while scrolling; `content-visibility` (iOS 18+ only — older iPhones lay out every shelf); import maps (16.4+; older gets the old caching, by design); `fetchpriority` and `priority` (ignored before 17.2); the service worker being evicted after a few weeks unused; `100vh` against the collapsing toolbar; video fullscreen.

Ten minutes with your own phone (ideally an old one), on the deployed branch:

1. **Cold start on mobile data.** Clear the site's data, turn Wi-Fi off, open the site. Count seconds to the billboard's title. Then close the tab and open it again: it should be about as fast as on Wi-Fi.
2. **Airplane mode, then back.** With Home open, airplane mode on: the banner appears, Home stays. Off: the banner goes, a tap on Movies works.
3. **iPhone, Safari and installed app:** the nav, tab bar and billboard sit clear of the island and the home indicator; nothing jumps when the toolbar collapses on scroll; rotate and rotate back on Home, a title page and the player.
4. **Scroll Home fast, top to bottom and back**, on the oldest phone in the house, glass look. Does the tab bar's text stay readable over what passes under it, and does anything stutter?
5. **Open a title, Back, open another, Back — ten times.** Does Back get slower? (The leak.)
6. **Text size.** iOS: Settings → Display → Text Size at maximum; Android: font size "largest". Look at Home, a title page and Settings for anything clipped or overlapping.
7. **Reduce Motion on:** the billboard should stop turning and nothing should slide.
8. **A series page on mobile data** — do the episode stills arrive, and how fast?
9. **Chrome on Android, `chrome://inspect` from a computer → Performance → reload Home.** Look at the first long "Layout" in the trace. If it is over 100 ms on the phone itself, that is the font question above.
10. **Data.** Android: Settings → Network → App data usage for the browser, before and after five minutes of browsing with Data saver on in Aurora. Expect 3–4 MB.
